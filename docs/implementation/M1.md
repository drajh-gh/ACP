      proposal replays by canonical digest.
- [x] Enforce one active or recovering writer lease per canonical target key,

- [x] Persist approval envelopes, precondition snapshots, effect evaluations,

- [x] Pin immutable policy and adapter definitions by exact version in workflow

- [x] Couple receipts to effect state transactionally and require exact,
      outcome-sensitive reconciliation before leaving `unknown_outcome`.
- [x] Implement deny-by-default, expiring capability-grant assessment.
- [x] Prevent cursor advancement without durable processing and complete source
      coverage.
- [x] Execute both forward and reverse migrations on PostgreSQL 18.6, upgrade
      a populated `0001` schema, and run database-level negative invariant
      tests.
- [x] Implement transactional PostgreSQL mission/event, effect, lease, workflow
      run, and durable-subscription stores.
- [x] Add immutable published definitions/bindings, cross-project foreign keys,
      version checksums, and exact completion-evaluation constraints.
- [x] Integrate a typed DBOS workflow shell with stable IDs, persisted run

      coordination, and durable approval waits.
- [x] Atomically create the ACP workflow projection and enqueue the top-level
      DBOS workflow in the same PostgreSQL transaction.
- [x] Treat approval messages only as wakeups, then load and validate the exact
      persisted approval/effect evaluation before authorization.
- [x] Gate `revalidating → executing` in PostgreSQL on a current covered
      approval, unpaused runtime controls, the exact fenced writer lease, and
      an immutable unexpired pre-effect observation matching the approved
      snapshot and current proposal/payload digests.
- [x] Require effects to begin as proposals and make `verified` reachable only
      through a receipt containing one ordered, matched, observed, timestamped,
      evidence-backed result for every immutable verification-plan step.
- [x] Implement resource-lease acquisition, heartbeat, expiry, release, and
      recovery acquisition.
- [x] Persist runtime provenance identities as well as versions, bind each
      record to one immutable workflow/profile/policy/completion tuple, and
      reject effect or runtime projection provenance outside its mission and
      adapter context.
- [x] Add database-enforced unknown-outcome reconciliation before retry.
- [x] Implement global/project kill-switch reads and optimistic transactional
      updates with append-only, monotonic audit events and immutable,
      exact-scope, time-bounded, single-use unpause authorizations; missing
      global control fails closed.
- [x] Bind durable approval-subscription replay to an absolute expiry and a
      semantic digest of its complete wait identity.
- [x] Add idempotent DBOS cancellation/reconciliation that verifies DBOS and
      ACP identity before cancellation, recursively cancels children, projects
      the event/open subscription atomically, and preserves terminal workflow
      or mission outcomes when either wins a race, including on a repeated
      cancellation request after DBOS has already recorded cancellation.
- [x] Keep in-flight DBOS control pinned to its persisted application version
      across worker rollouts, project ordinary DBOS errors and exhausted
      recovery attempts as evidenced terminal ACP failures, and reconcile a
      cursor-bounded batch of still-active or partially failed projections at
      worker startup and every 30 seconds thereafter; malformed items are
      reported without starving later items in the batch.
- [x] Persist an append-only cancellation intent before asking DBOS to cancel,
      then reconcile stranded `CANCELLED` workflows from the periodic sweep so
      a process exit between the DBOS and ACP commits converges safely.
- [x] Add a strict runtime compatibility negotiation contract and block new
      workflow projection/enqueue when the pinned API, worker, database-schema,
      or workflow versions do not match the observed runtime.
- [x] Record transition-specific runtime provenance and freeze terminal worker
      results.
- [x] Serialize effect execution admission against control changes, approval

- [x] Reject blank or structurally invalid runtime provenance and bind every

- [x] Mediate deterministic adapter execution, persist classified lost-response

## Deferred beyond M1

- [ ] Wire the compatibility contract into the Codex-plugin/hosted-API
      connection and console once those M2/M5 transport and UI surfaces exist;
      new PostgreSQL workflow submission already fails closed on mismatches.
- [ ] Persist real subprocess identity and prove timeout/cancellation cleanup;
      M2 now includes the pinned Codex SDK transport and propagates bounded
      cancellation into it, but the public SDK does not expose the spawned PID,
      start token, or process-tree handle needed to connect that subprocess to
      ACP's worker-process journal and prove orphan cleanup.
- [ ] Remove the final DBOS cancellation race once its public API supports a
      status-guarded cancellation transition. DBOS 4.27.6 can move a workflow
      to `MAX_RECOVERY_ATTEMPTS_EXCEEDED` between ACP's identity/status read and
      `cancelWorkflow`, while the SDK cancellation update excludes only
      `SUCCESS` and `ERROR`. ACP detects and projects either terminal-failure
      status before cancellation, but cannot make that cross-schema transition
      atomic without binding to private DBOS tables.

## Evidence limits

On 2026-09-04, `0001` and `0002` applied successfully to the official
`postgres:18.6-alpine3.24` image (digest
`sha256:d3e1620b530c944afa6e887d22eb899824da68e19c52024bf98f5220c88a65b2`).
An existing `0001` provenance row survived the `0002` upgrade. The invariant
fixture passed, including target-shape denial, proposal-first and approval
gates, scalar and structured precondition snapshots, strict boolean matching,
nonblank observation identity, fresh precondition read-back, fenced execution,
monotonic single-use kill-switch
events, exact-scope unpause authorization, complete evidence-backed receipt
verification, future-timestamp denial, context-packet-bound worker provenance,
context-bound effect provenance, retry denial, project-scoped available
reconciliation evidence that exactly matches the observation source, digest,
and time, outcome-specific observed state, cross-effect and outcome-sensitive
reconciliation, per-step verified-receipt evidence that exactly matches the
observed digest and timestamp, immutable mission identity, transition-specific
mission provenance, same-project runtime-control provenance, fenced execution
admission against every authority mutation, immutable completion attribution,
terminal-result immutability, and durable subscription checks. Legacy
completion evaluations survived migration only as explicitly
unverified records, while unrecoverable active legacy missions fail migration
preflight. A two-session probe also proved that a transaction begun before a
concurrent safety pause waits on the shared authority fence and observes the
pause after it commits. Both down migrations removed the schema. The container
used temporary storage, exposed no host port, and was auto-removed.

DBOS registration and calls are compiler-checked against 4.27.6. The top-level
enqueue uses `DBOSClient.enqueueInTransaction`; workflow event IDs and times use
DBOS durable primitives. Local tests reject non-runnable submission and
mismatched cancellation identities, recognize the SDK cancellation classes,
preserve terminal mission state during cancellation reconciliation, and prove
that an already-cancelled DBOS retry does not overwrite terminal ACP state.
They also cover old-version in-flight control, recovery-exhaustion projection,
ordinary DBOS-error projection, idempotent terminal-failure replay, terminal
race preservation, cursor-bounded periodic reconciliation, durable
cancellation-intent recovery, and fail-closed compatibility admission before
projection or DBOS enqueue. The opt-in live recovery check runs on the supported
host Node runtime against a resource-limited PostgreSQL container published
only on a random loopback port. It force-kills the first DBOS worker after a
durable checkpoint, launches a replacement with the same application version
and executor identity, and proves both checkpointed steps have exactly one
durable invocation. The synthetic effect test commits its target mutation,
loses the response, persists `unknown_outcome`, denies retry, reconstructs the
adapter, reconciles the idempotency key, and independently verifies one total
mutation. Effect execution and every mutation that can change its authority use
one database-enforced transaction-level advisory fence; the execution statement
reads current controls, approval state, evaluations, and lease state only after
acquiring it. No claim is made that generic subprocess cleanup or atomic
cancellation against a simultaneous DBOS dead-letter transition works until
those post-M1 gates are closed.
